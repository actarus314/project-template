The repo controls, from commit to production

First where the code goes, then what verifies it — at what point, with what tool, triggered by what. The distinction that structures everything: a private repo on the Free plan has no ruleset — the controls run, but nothing requires them.

Dormant in private — activates when going public

The flow — where the code goes

The single principle: main is production. We never write to it directly — the only way in is a pull request with green CI. Everything else follows from that.

What decides the flow: a single question

"Is there a host to VALIDATE before production?" — that's the staging capability, and only that one. Not the language, not Docker.

A node project with no host to validate does not need develop. A Pages site packaged as an image doesn't either — the image is the page. Publishing an artefact (tag → ghcr image) is an independent capability: it attaches to both flows below.

Without staging — GitHub Flow, two branches are enough

This is the case of a Pages site, and also that of a static site packaged as an image so third parties can self-host it. Nothing to validate upstream → a develop would be an empty ritual, and a long-lived branch nobody uses drifts until the merge stops happening.

pages: merging deploys artefact: the tag publishes the image — independent capability, optional here
1 · Branch

Always from main.git switch -c feat/<topic>

2 · Commit

The hook refuses a secret.git commit

3 · Open the PR

The CI runs before the code touches main.gh pr create --fill

4 · Merge

Only if the CI is green — not gh pr checks (the Checks permission cannot be granted).gh run list --commit "$(gh pr view <n> --json headRefOid --jq .headRefOid)"gh pr merge --squash

With staging — three tiers, because there's a host to validate

Here develop earns its place: there's a real host to validate before production. And prod doesn't follow a branch, it follows a pinned tag — we promote an artefact, not a branch.

main — production develop — staging (host) feat/… — the work PR · CI green the only passage — nothing else writes to these branches

This is NOT two pull requests per change

That's the classic confusion, and it would make the flow unbearable. The feat/ branches pile up in develop — one PR each, that's the normal pace of work.

develop → main happens only when publishing a version: a single PR for N changes. Solo, that's roughly once a week, not once per commit.

Why the pull request even solo, even in private

Without a PR, we push to main and the CI runs after: it becomes an autopsy, not a barrier — it records the damage on the branch we just declared "production". With a PR, it runs before. That's the whole difference between knowing and preventing.

This has already happened: a direct push to main removed a user: directive; the image shipped as :latest, the prod host pulled it, and production went down — discovered after the fact.

Where we do NOT tighten the screws — too many controls kills the control: no lint at pre-commit · only one blocking control locally, secrets (vital, instant, irreversible once pushed) · zero mandatory review (required_approving_review_count = 0): solo, self-approving would be theater.

The pipeline

Seven stages. Each one catches what the previous one couldn't see — a secret at commit, an injection in a PR, a tag moved after the release.

Local commitdev machine

No secret in the staged files. gitleaks — hook .githooks/pre-commit, armed by git config core.hooksPath .githooks. Bypassable with --no-verify: the CI replays it on the full history.

Local pushdev machine

No direct push to main / develop. pre-push hook — this is the substitute for the missing ruleset as long as the repo is private. Lets branch creation through, refuses direct writes.

Secret detected in the push, server-side. push protection — native GitHub, automatic. Unavailable on a private repo on Free.

Pull requestjob checks

Secrets across the full history, not just the diff. gitleaks — pinned binary + checksum. The net that cannot be bypassed.

Application code flaws. semgrep — p/security-audit + p/owasp-top-ten rulesets. Analyzes file by file: it precedes CodeQL, it doesn't replace it.

Vulnerable dependencies (all manifests, -r .). osv-scanner — OSV database. It's the equivalent of dependency-review, except this one works in private.

The workflows themselves: syntax, shell, ${{ }} injection. actionlint · zizmor — a workflow is code, and it's the most direct attack surface.

The code does what it claims. npm test · npm run typecheck · npm audit · node --check — depending on the toolchain (--type).

Cross-file static analysis (data flow). CodeQL — requires GitHub Advanced Security on a private repo. Its license even forbids local use on private code.

Incoming dependency + licenses. dependency-review — blocks before the merge, where Dependabot only alerts after.

Pull requestjob build-check

Docker image CVEs — CRITICAL/HIGH fail the PR. docker build --load › trivy — scanning at deploy time would be too late: the image is already tagged and prod pins it.

Mergeserver

PR mandatory · required checks · no force-push. main / develop rulesets — set up by configure-repo.sh. In private, they don't exist: a red PR can be merged.

Tag v*release

Image published to ghcr. docker-publish.yml › build-push — triggered by the tag push.

The tag can't be moved or deleted. tags ruleset — without it, the version pin in prod guarantees nothing: the tag could point elsewhere tomorrow.

A release's assets can no longer be replaced. immutable releases — not retroactive: set it up before v1, otherwise it's too late.

Productionhost

Is the image actually pullable? curl ghcr.io/v2/…/manifests — tested anonymously, the way the prod host does. A green "Publish image" job proves nothing. The default depends on the owner: public by default on a personal account, PRIVATE by default on an ORGANIZATION (anonymous pull = 403). The script tests, and only asks for action if the test fails.

The private → public switch

The nominal cycle: the repo is born private, it becomes public. Everything that was dormant activates all at once — it's the most dangerous moment of its life.

While private

Everything runs. Nothing is required.

  • gitleaks (hook + CI, full history)
  • pre-push hook: no direct write to main
  • semgrep · osv-scanner
  • actionlint · zizmor · trivy
  • tests · typecheck · Renovate + Dependabot alerts
  • No ruleset — a red PR can be merged
→flip

Going public

The server enforces what discipline used to hold.

  • main, develop, tags rulesets
  • Required checks before merge
  • Secret scanning + push protection
  • CodeQL — scans the whole history at once
  • dependency-review · immutable releases
  • Private vulnerability reporting

The hole, and how it's held

In private, discipline is the only safety net — so it's tooled

On a private repo on Free, GitHub would accept a direct push to main, and a red PR can be merged. A discipline that's only written down doesn't exist: it's carried by tools everywhere possible.

The pre-commit hook refuses a secret. The pre-push hook refuses direct writes to main — it's the missing ruleset, brought back onto the developer's machine. Both can be bypassed with --no-verify: a decision, not an accident.

Only one point stays human: never merge a red PR. No hook can intercept it, the merge happens server-side. The rule therefore lives in AGENTS.md and CONTRIBUTING.md, along with its command.

⚠️ This is not gh pr checks: it requires the Checks permission, absent from the UI of fine-grained PATs — so impossible to grant. The rule was written everywhere, and unenforceable everywhere. → gh run list --commit <sha>, and green ⇔ every expected workflow is completed / success (a workflow that's absent is not a green: it just hasn't reported yet). Detail: standard §18.

And CodeQL never ran during all that time — hence semgrep and osv-scanner, which continuously clear ground so that at the flip what's left is a residue, not an avalanche.
