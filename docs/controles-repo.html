Les contrôles d'un repo, du commit à la production

D'abord où va le code, ensuite ce qui le vérifie — à quel moment, par quel outil, déclenché par quoi. La distinction qui structure tout : un repo privé en plan Free n'a aucun ruleset — les contrôles tournent, mais rien ne les exige.

Actif dès la phase privée
Dort en privé — s'active au passage en public
Étage bloquant (rien ne passe sans lui)

Le flux — où va le code

Le principe unique : main est la production. On n'y écrit jamais directement — la seule porte d'entrée est une pull request dont la CI est verte. Tout le reste en découle.

Ce qui décide du flux : une seule question

« Existe-t-il un host à VALIDER avant la production ? » — c'est la capacité staging, et elle seule. Pas le langage, pas Docker.

Un projet node sans host à valider n'a pas besoin de develop. Une page Pages qu'on package en image non plus — l'image est la page. La publication d'un artefact (tag → image ghcr) est une capacité indépendante : elle se greffe sur les deux flux ci-dessous.

Sans staging — GitHub Flow, deux branches suffisent

Le cas d'un site Pages, et aussi celui de rozo-bridge packagé en image pour que des tiers l'auto-hébergent. Rien à valider en amont → une develop serait un rituel vide, et une branche longue que personne n'utilise dérive jusqu'à ce que le merge cesse d'avoir lieu.

pages : le merge déploie artefact : le tag publie l'image — capacité indépendante, optionnelle ici
1 · Brancher

Toujours depuis main.git switch -c feat/sujet

2 · Commiter

Le hook refuse un secret.git commit

3 · Ouvrir la PR

La CI tourne avant que le code touche main.gh pr create --fill

4 · Merger

Seulement si la CI est verte — pas gh pr checks (permission Checks non accordable).gh run list --commit "$(gh pr view <n> --json headRefOid --jq .headRefOid)"gh pr merge --squash

Avec staging — trois étages, parce qu'il y a un host à valider

Ici develop gagne sa place : il existe un vrai host (le NUC) à valider avant la production. Et la prod ne suit pas une branche, elle suit un tag épinglé — on promeut un artefact, pas une branche.

main — la production develop — staging (NUC) feat/… — le travail PR · CI verte le seul passage — rien d'autre n'écrit sur ces branches

Ce n'est PAS deux pull requests par changement

C'est la confusion classique, et elle rendrait le flux insupportable. Les feat/ s'accumulent dans develop — une PR chacune, c'est le rythme normal du travail.

develop → main n'arrive qu'au moment de publier une version : une seule PR pour N changements. En solo, c'est de l'ordre d'une fois par semaine, pas une fois par commit.

Pourquoi la pull request même seul, même en privé

Sans PR, on pousse sur main et la CI tourne après : elle devient une autopsie, pas un barrage — elle constate les dégâts sur la branche que l'on vient de déclarer « production ». Avec une PR, elle tourne avant. C'est toute la différence entre savoir et empêcher.

Ça s'est déjà produit : sur dEURO, un push direct sur main a retiré une directive user: ; l'image est partie en :latest, le NUC l'a tirée, la production est tombée — découverte après coup.

Là où l'on ne serre PAS la vis — trop de contrôles tue le contrôle : aucun lint au pre-commit · un seul contrôle bloquant en local, les secrets (vital, instantané, irréversible une fois poussé) · zéro relecture obligatoire (required_approving_review_count = 0) : en solo, s'auto-approuver serait un théâtre.

Le pipeline

Sept étages. Chacun attrape ce que le précédent ne pouvait pas voir — un secret au commit, une injection en PR, un tag déplacé après la release.

Commit localposte de dev

Aucun secret dans les fichiers stagés. gitleaks — hook .githooks/pre-commit, armé par git config core.hooksPath .githooks. Contournable avec --no-verify : la CI rejoue sur l'historique complet.

Push localposte de dev

Pas de push direct sur main / develop. hook pre-push — c'est le substitut du ruleset absent tant que le repo est privé. Laisse passer la création d'une branche, refuse l'écriture directe.

Secret détecté dans le push, côté serveur. push protection — natif GitHub, automatique. Indisponible sur un repo privé en Free.

Pull requestjob checks

Secrets sur l'historique complet, pas seulement le diff. gitleaks — binaire épinglé + checksum. Le filet qu'on ne peut pas contourner.

Failles du code applicatif. semgrep — rulesets p/security-audit + p/owasp-top-ten. Analyse fichier par fichier : il précède CodeQL, il ne le remplace pas.

Dépendances vulnérables (tous manifestes, -r .). osv-scanner — base OSV. C'est l'équivalent de dependency-review qui, lui, fonctionne en privé.

Les workflows eux-mêmes : syntaxe, shell, injection ${{ }}. actionlint · zizmor — un workflow est du code, et c'est la surface d'attaque la plus directe.

Le code fait ce qu'il prétend. npm test · npm run typecheck · npm audit · node --check — selon la toolchain (--type).

Analyse statique inter-fichiers (flux de données). CodeQL — exige GitHub Advanced Security sur un repo privé. Sa licence interdit même l'usage local sur du code privé.

Dépendance entrante + licences. dependency-review — bloque avant le merge, là où Dependabot n'alerte qu'après.

Pull requestjob build-check

CVE de l'image Docker — CRITICAL/HIGH font échouer la PR. docker build --load › trivy — scanner au déploiement serait trop tard : l'image est déjà taguée et la prod l'épingle.

Mergeserveur

PR obligatoire · checks requis · pas de force-push. rulesets main / develop — posés par configure-repo.sh. En privé, ils n'existent pas : une PR rouge peut être mergée.

Tag v*release

Publication de l'image sur ghcr. docker-publish.yml › build-push — déclenché par le push du tag.

Le tag ne peut être ni déplacé ni supprimé. ruleset tags — sans lui, le pin de version en prod ne garantit rien : le tag peut pointer ailleurs demain.

Les assets d'une release ne peuvent plus être remplacés. immutable releases — non rétroactif : à poser avant la v1, sinon c'est trop tard.

Productionhost

L'image est-elle réellement tirable ? curl ghcr.io/v2/…/manifests — testé anonymement, comme le fait le host de prod. Un job « Publish image » vert ne prouve rien. Le défaut dépend du propriétaire : public d'office sur un compte perso, PRIVÉ d'office sur une ORGANISATION (pull anonyme = 403). Le script teste, et ne réclame le geste que si le test échoue.

La bascule privé → public

Le cycle nominal : le repo naît privé, il devient public. Tout ce qui dormait s'active d'un seul coup — c'est le moment le plus dangereux de sa vie.

Pendant le privé

Tout tourne. Rien n'est exigé.

  • gitleaks (hook + CI, historique complet)
  • hook pre-push : pas d'écriture directe sur main
  • semgrep · osv-scanner
  • actionlint · zizmor · trivy
  • tests · typecheck · Renovate + Dependabot alerts
  • Aucun ruleset — une PR rouge peut être mergée
→flip

Au passage en public

Le serveur applique ce que la discipline retenait.

  • Rulesets main, develop, tags
  • Checks requis avant merge
  • Secret scanning + push protection
  • CodeQL — analyse tout l'historique d'un coup
  • dependency-review · immutable releases
  • Private vulnerability reporting

Le trou, et comment il est tenu

En privé, la discipline est le seul filet — donc elle est outillée

Sur un repo privé en Free, GitHub accepterait un push direct sur main, et une PR rouge peut être mergée. Une discipline qui n'est qu'écrite n'existe pas : elle est portée par des outils partout où c'est possible.

Le hook pre-commit refuse un secret. Le hook pre-push refuse l'écriture directe sur main — c'est le ruleset manquant, ramené sur la machine du développeur. Les deux se contournent avec --no-verify : une décision, pas un accident.

Un seul point reste humain : ne jamais merger une PR rouge. Aucun hook ne peut l'intercepter, le merge se joue côté serveur. La règle vit donc dans AGENTS.md et CONTRIBUTING.md, avec sa commande.

⚠️ Ce n'est pas gh pr checks : elle exige la permission Checks, absente de l'UI des PAT fine-grained — donc impossible à accorder. La règle était écrite partout, et inapplicable partout. → gh run list --commit <sha>, et vert ⇔ tous les workflows attendus sont completed / success (un workflow absent n'est pas un vert : il n'a pas encore rapporté). Détail : standard §18.

Et CodeQL n'a jamais tourné pendant tout ce temps — d'où semgrep et osv-scanner, qui défrichent en continu pour qu'au flip il reste un résidu, pas une avalanche.
